# AGENTS.md — правила работы над проектом «Составь слова»

Автономное офлайн-приложение для Android (Kotlin 2.2, Jetpack Compose): из длинного слова нужно составить как можно больше слов.
Модули: `:core` (чистый Kotlin/JVM, вся логика), `:app` (UI, данные, DI), `tools/` (Python: сборка словаря и данных).
Этот файл главный. README.md читай по разделам и только когда нужно (архитектура, экраны, правила игры).

Текущий проверенный снимок: `docs/PROJECT_STATUS.md`. В `data/` — 23 393 слова и 35 947 локальных толкований для 23 390 слов; `HAS_DEFINITIONS=true`. Последние доступные проверки: 71 Python-тест и 42 теста `:core` прошли. Android-компиляция, lint и проверка на устройстве не подтверждены из-за отсутствующего настроенного SDK. Release остаётся заблокированным ручным аудитом. Числа сверять с манифестом при следующей регенерации.

## 1. Быстрый цикл проверки

Работай от малого к большому: после каждой правки запускай самую узкую проверку, полный гейт запускай один раз перед коммитом.

| Что менял | Что запускать |
|---|---|
| Логика в `:core` | `./gradlew :core:test --tests 'com.example.sostavslova.core.<Класс>Test' --console=plain`, затем весь `:core:test` |
| Kotlin в `:app` (промежуточно) | `./gradlew :app:compileDebugKotlin --console=plain` |
| Тесты в `androidTest` | `./gradlew :app:compileDebugAndroidTestKotlin`; `:app:connectedDebugAndroidTest` только при наличии эмулятора или устройства |
| Строки, ресурсы, манифест | `./gradlew :app:lintDebug` |
| `tools/` | `python3 -m unittest discover tools/tests` |
| `orchestrator/` | `bash -n orchestrator/run.sh`, затем `bash orchestrator/run.sh --check orchestrator` |
| `data/`, `legal/` | `./gradlew :app:verifyDictionaryLicenses`, затем `:core:test` |
| Gradle, R8, манифест, подпись | `./gradlew :app:assembleRelease` |
| Гейт перед коммитом | `:core:test` и `:app:assembleDebug` (он сам запускает `syncDictionaryAssets` и `verifyDictionaryLicenses`) плюс строки выше по типу правки |

Если команду запустить нельзя (нет сети, Android SDK, эмулятора), скажи об этом явно и пометь пункт «не проверено». Не имитируй вывод и не пропускай тесты молча.

## 2. Карта репозитория

```
core/   Alphabet (нормализация, ё→е), WordIndex (поиск по мультимножеству букв), GameState,
        Levels, RussianPlural; тесты и TestData (данные тесты берут из ../data)
app/    data/    WordRepository, LevelsRepository, ProgressRepository (DataStore),
                 DefinitionsRepository, SqliteDefinitionsRepository
        di/      AppContainer
        nav/     Destination, WordsNavHost
        ui/      <экран>/ (Screen + ViewModel), components/, theme/
        src/debug         каталог компонентов
        src/androidTest   инструментальные тесты
tools/  build_dictionary.py, overrides/ (add.txt, remove.txt), tests/
orchestrator/ последовательное выполнение задач разработки, run.sh --check, tests/ (вне Android-приложения)
data/   words.txt, levels.json, golden_search.json, word_sources.jsonl.gz, manifest.json (ГЕНЕРИРУЮТСЯ)
legal/  лицензии и инвентарь библиотек (копируются в assets)
```

Где что менять: правило игры → `:core` плюс тест; экран → `ui/<экран>/`; сохранение → `ProgressRepository`; словарь и данные → `tools/` плюс регенерация.

## 3. Жёсткие правила

1. **`:core` — источник истины для логики** (нормализация, поиск, состояние игры, уровни, склонение, подсказки, маскирование ответа). Не дублируй её в `:app`. Меняешь правило: сначала тест в `:core`, затем код.
2. **В приложении нет сети:** не добавляй `INTERNET` и другие разрешения, библиотеки аналитики, рекламы, краш-репортинга, HTTP-вызовы. Исключение: офлайн-инструменты в `tools/` могут ходить в сеть только по явному флагу командной строки; ключи берутся из переменных окружения и не попадают в репозиторий.
3. **Данные не правятся вручную.** `data/*` генерируются `tools/`, в `app/src/main/assets/` их копирует `syncDictionaryAssets`. Не добавляй слова в `words.txt` вручную и не используй `overrides/add.txt` как обход.
4. **Определения опциональны:** приложение должно работать без базы определений.
5. **Никакого HTML** в выводе: только `Text` Compose; переводы строк `\n`.
6. **Строки интерфейса только в `res/values/strings.xml`** (русский язык), даже «временные»; числа со словами через `RussianPlural`.
7. **Состояние:** ViewModel + `StateFlow`, одностороннее движение данных; тяжёлая работа в `Dispatchers.Default` или `IO`, UI-поток не блокировать.
8. **Без `!!`, `GlobalScope`, `runBlocking` на UI-потоке.**
9. **Зависимости и версии:** новые библиотеки, смену AGP, Kotlin, `compileSdk`, `minSdk`, `targetSdk` делай только по явной задаче. Версии стабильные и совместимые, JVM 21 toolchain.
10. **Секреты не коммитятся:** `*.keystore`, `keystore.properties`, API-ключи, токены.
11. **Производительность:** не запускай полный перебор словаря на старте приложения и в UI-потоке; считай заранее в `tools/` или кэшируй.
12. **Совместимость сохранений:** новые поля в сохраняемых моделях (DataStore, JSON) только со значениями по умолчанию, чтобы старые сохранения читались. Прогресс уровня привязан к `level.word`: смена слова уровня сбрасывает звёзды.

## 4. Данные и словарь

* Порядок работы с данными: правка `tools/` → тесты `tools/tests` → регенерация на локальном дампе → обновлённые `manifest.json` и хэши → `:app:verifyDictionaryLicenses` → `:core:test`.
* Для регенерации нужен локальный дамп Викисловаря (Kaikki, путь и SHA-256 сверяются с `manifest.json`). Нет дампа или хэш не совпал: остановись и сообщи. Ничего не придумывай и не подделывай.
* Скрипты детерминированы: одинаковый вход даёт одинаковые файлы и хэши.
* Текущая игровая база собирается `tools/clean_dictionary.py` (или режимом `clean` в `build_game_data.py`, он выбран по умолчанию). Вход — зафиксированные 113 413 слов, локальный дамп и частотный список. Прежние overrides, лимиты кандидатов и наличие определений не определяют состав новой базы. Параметры — блок `cleanup` в `tools/selection_config.json`.
* Решение владельца: слова уровней сохраняются с отчётом об исключениях. Согласованы четыре замены: `намеривание` → `взвешивание`, `перетекание` → `переливание`, `передвигание` → `магнитофон`, `симфонизация` → `велосипед`; числовые пороги сохраняются. У «переливание» буква задания «п», у «магнитофон» остаётся «г», у «велосипед» — «с». Другие слова и пороги уровней не менять без согласования.
* Золотой список частотных слов (`core/src/test/resources/frequent_nouns_golden.txt`) сохраняется как проверочная выборка, но не как список принудительного включения. Отказы отражаются в `manifest.selection.reference_checks` и отчёте; сам список не сокращать ради тестов.
* Отбор игровых слов не должен зависеть от упоминаний авторов или словарей в тексте статей.
* Тесты `tools/` работают на синтетических данных. Не копируй в репозиторий, тесты и промпты тексты чужих словарных статей.

## 5. Права на определения

* Определения бывают двух видов: собственные (созданы без подачи текстов Викисловаря в модель) и из Викисловаря (с атрибуцией по CC BY-SA). Защищённые сторонние словари и сайты-агрегаторы не используются как источники определений.
* Предыдущий эксперимент от 2026-11-06: ИИ-оценка отменена, временные определения с непроверенным статусом прав извлечены из локального дампа Kaikki для 60 000 кандидатов. Эти артефакты остаются в кэше и не задают состав новой игровой базы. Происхождение сохраняется, определения подлежат замене перед публикацией. Подробности: `docs/decisions/2026-11-06-provisional-definitions.md`. Новое решение: `docs/decisions/2026-11-06-clean-game-vocabulary.md`.
* По последующей явной задаче владельца определения из того же локального дампа собираются для очищенного словаря `tools/build_local_definitions.py`, а `HAS_DEFINITIONS=true` включает их в игру. Состав словаря и уровни при этом не меняются. Полные толкования хранятся с источником, в подсказках обрабатываются `core/DefinitionHint`: формы, ближайшее родство и эвристика корня, замена на `***`, отказ от малоинформативных подсказок. Правила и команды — `docs/LOCAL_DEFINITIONS.md`. Статус прав остаётся временным, ручной аудит не пройден, release не разрешён.
* Лицензию собственных определений определяет владелец. Не придумывай её, оставляй явный плейсхолдер.
* Сборка с определениями для релиза допускается только после пройденного ручного аудита (`manifest.definitions.audit.passed`).
* Подсказка не должна раскрывать ответ: само слово и однокоренные слова в тексте подсказки маскируются.

## 6. Тесты и качество

* `:core`: сначала тест, потом код. Для бага сначала падающий тест, потом исправление.
* Не ослабляй и не удаляй тест, чтобы он позеленел. Если ожидание изменилось по делу, объясни это в отчёте.
* UI: `testTag` в формате `<экран>_<элемент>` в snake_case (например, `game_hint`, `about_word_count`). Новое поведение покрывай тестом. Не используй `Thread.sleep`: только ожидания Compose (`waitUntil`, idling).
* Тесты не зависят от сети, порядка выполнения и текущего времени.
* Соглашения: экраны `HomeScreen`, `GameScreen`; ViewModel `HomeViewModel`; состояние UI `data class XUiState`.

## 7. Как работать быстро, не теряя качества

* Читай адресно: `grep -rn` или `rg` по символу, затем нужный файл. Не читай целиком `data/words.txt` (около 113 тыс. строк), `data/word_sources.jsonl.gz`, `data/golden_search.json`, `definitions.db`: используй `head -n 30`, `grep -c`, короткие скрипты на Python.
* Перед правками назови в 2–3 строках, какие файлы изменишь. Правь пакетом, затем одна проверка. Не запускай полную сборку после каждой строки.
* Не регенерируй данные без необходимости: это долго и требует внешнего дампа.
* Делай ровно то, что просит задача: без попутного рефакторинга, форматирования чужого кода и абстракций «на будущее». Нашёл смежную проблему: запиши в отчёте, не чини молча.
* Переиспользуй готовое: `TestData`, фейки из `androidTest`, компоненты `ui/components/`, строки и `RussianPlural`.
* Большая задача: разбей на атомарные коммиты (одна проблема, один коммит).
* Независимые задачи не трогают одни и те же файлы одновременно.

## 8. Когда остановиться и спросить владельца

Не решай сам, а спроси: финальный `applicationId`; ключи подписи; лицензия и формулировки про собственные определения; смена слов и порогов уровней; выбор ИИ-провайдера и ключи; новые зависимости; изменение правил игры, звёзд и подсказок; регенерация данных без дампа; публикация. Остальное (имена, внутреннее устройство в пределах задачи, добавление тестов) решай сам.

## 9. Известные ловушки (сверяйся с `git log`, часть может быть уже исправлена)

* Release мог подписываться debug-ключом, а `debug.keystore` нет в репозитории (`*.keystore` в `.gitignore`). Не создавай и не коммить ключи; если сборка падает на keystore, сообщи.
* `applicationId` в `app/build.gradle.kts` может быть заглушкой AI Studio. Не меняй без указания владельца.
* `HAS_DEFINITIONS=true` включён по явной задаче владельца вместе с локальной БД. Отсутствующая БД должна обрабатываться безопасно; непроверенная БД не допускается в release. Не обходи аудит и не отключай уже согласованные определения без задачи.
* Поиск: слова нормализуются (ё→е), слово не короче 3 букв, исходное слово не засчитывается, букву можно использовать не чаще, чем она встречается в исходном слове.
* `GameViewModel.onGameOpened()` вызывается на каждый `ON_RESUME` и перезагружает игру. Не усугубляй, а если исправляешь, держи изменение в отдельной задаче.
* Тесты `:core` читают данные из `../data` (через ресурсы теста), поэтому правка `data/` влияет на `:core:test`.
* `preBuild` зависит от `syncDictionaryAssets` и `verifyDictionaryLicenses`: сборка падает, если хэши данных и `manifest.json` расходятся.

## 10. Отчёт и коммиты

Отчёт: (1) изменённые файлы и что сделано; (2) команды проверки и их результат; (3) что не проверено и почему; (4) риски и смежные находки (не больше 5 строк).
Коммит: один на задачу, формат `<ID или область>: <кратко>`, без «WIP».

## 11. Definition of Done

- [ ] Выполнено ровно то, что просила задача; лишнего нет.
- [ ] Для изменённой логики есть тест; все тесты из §1 по типу правки прошли.
- [ ] Строки в `strings.xml`, нет `!!`, нет блокировок UI-потока, нет новых разрешений и зависимостей без решения владельца.
- [ ] Данные не правились вручную; хэши и `manifest.json` согласованы.
- [ ] Отчёт составлен по §10, непроверенное названо.

## 12. Последовательный оркестратор

Инструкция: `orchestrator/README.md`. Очередь — `orchestrator/TASKS.md`, журнал —
`orchestrator/PROGRESS.md`, локальные логи — `orchestrator/.runtime/` (не коммитятся).
Примеры из `orchestrator/examples/` не входят в активную очередь.

* План: `bash orchestrator/run.sh --dry-run`; выполнение: `bash orchestrator/run.sh`.
  Запускать из корня проекта после сохранения изменений коммитом. Агентские задачи
  выполняются последовательно в `auto/tasks`; push по умолчанию отключён.
* В задаче указывать `gate: bash orchestrator/run.sh --check full`: тесты `tools/`,
  оркестратора, `:core:test` и `:app:assembleDebug`. Дополнительные проверки по §1
  добавлять через `&&`; для Gradle/R8/подписи требуется также `:app:assembleRelease`.
  Узкие профили `run.sh --check` нужны для промежуточной проверки и не заменяют полный гейт.
* Отсутствие JDK/SDK и провал ручного аудита — причины остановки, а не повод
  подменять проверку `skip` или ослаблять её. Оркестратор не устанавливает SDK,
  не регенерирует данные и не разрешает публикацию.
* Только внутри задания, полученного от оркестратора: не выполнять `git commit`,
  push, переключение ветки и изменение служебных файлов `orchestrator/`.
  Коммит и запись результата делает внешний процесс после успешного gate.
  При обычной работе над интеграцией эти файлы можно редактировать.
* Согласования из §8 действуют и для автоматических задач. Если без решения
  владельца продолжать нельзя, завершить ответ строкой `BLOCKED: <причина>`.
