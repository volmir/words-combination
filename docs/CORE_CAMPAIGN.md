# Модели и прогресс кампании v2 — CORE-01, CORE-02, CORE-03

Контракт правил: [CAMPAIGN.md](CAMPAIGN.md). Модели находятся рядом с `Levels.kt`
в чистом `:core`; `Level`, `LevelProgress`, `LevelRules` и клиенты v1 не изменены.

`Campaign(stages, levels, version=2, countMinLength=4)` содержит упорядоченные
уровни. `Stage(number, firstLevel, lastLevel)` задаёт включительный диапазон.
`CampaignLevel(number, word, stage, requiredStars, tasks)` хранит стабильный
словарный ключ сохранения `word`, номер, ссылку на этап и R. M (`maxStars`)
вычисляется из числа заданий, общий максимум — из уровней.

`CampaignTask` — закрытая иерархия параметров; `type: TaskType` выводится из
класса и не передаётся отдельно:

| Тип | Параметры помимо глобально уникального `id` |
|---|---|
| T1 | `n`: количество слов, минимум длины — `countMinLength` |
| T2 | `letter`, `n`: начальная буква, минимум длины — `countMinLength` |
| T3 | `minLength`, `hintTarget`: любой ответ L+, фиксированная цель подсказки |
| T4 | `targets`: непустой список фиксированных целей одного задания |
| T5 | `ending`, `minLength`: одно слово с окончанием и нужной длиной |
| T6 | `category`, `n`, `words`: ключ темы и полный список местных ответов |
| T7 | `letter`, `n`: количество слов, содержащих букву |

`CurrentCampaignLevel(level, game, completedTaskIds=emptySet(), hints=HintState())`
объединяет описание открытого уровня, существующий `GameState`, полученные ID
звёзд и состояние подсказок. Это контейнер данных; доступ и прогресс определяет
`CampaignRules`, подсказки — `HintRules`. Подключение хранилища относится к
следующим задачам. Клиент передаёт игру
для того же `level.word` и ID из `level.tasks`.

## Прогресс заданий — CORE-02

`TaskRules.submit(current, raw, campaign.countMinLength)` вызывает
`GameState.submit` и возвращает `TaskSubmission(result, evaluation)`.
Проверка допустимости ответа, запись в `found` и статистика остаются в
`GameState`. Задания считают только уникальные нормализованные ответы
текущего уровня; ответы других уровней не ограничивают ввод.

`TaskRules.evaluate(current, campaign.countMinLength)` позволяет пересчитать
прогресс после восстановления. Оба пути возвращают `TaskEvaluation`:
`state` с объединёнными `completedTaskIds`, `progress` в порядке заданий,
`newlyCompletedTaskIds` для выдачи новых звёзд и `stars` — общее число звёзд.
Возвращённый `state` нужно сохранить и использовать при следующих вызовах.
Повторный пересчёт не выдаёт звезду снова; сохранённая звезда не пропадает,
даже если текущий список ответов неполон. Если ID потерян, но `found` уже
выполняет задание, звезда восстанавливается.

`TaskProgress(id, current, target, completed)` содержит числитель, ограниченный
целью, и признак выполнения с учётом сохранённой звезды. Поэтому после
восстановления звезды числитель может быть меньше цели при `completed=true`.
T1/T2 применяют `countMinLength`, T2 проверяет только первую букву. T3
принимает любой ответ длины `minLength` и больше, независимо от `hintTarget`.
T4 считает найденные назначенные цели и выдаёт одну звезду только за весь
список. T5 требует одновременно суффикс и минимальную длину. T6 использует
локальный `words`; T7 считает слова с буквой, а не число её вхождений.
Одно слово может выполнить несколько заданий. Трёхбуквенный «кот» сохраняется
и учитывается в статистике, не продвигает T1/T2 при минимуме 4, но подходит
для соответствующих T6/T7. API ожидает проверенные параметры кампании и
принятые ответы в `GameState.found`; повторной словарной проверки здесь нет.

## Доступ, возвраты и финал — CORE-03

`CampaignProgress` — сохраняемый снимок: `levels=emptyMap()` по ключу
`CampaignLevel.word`, `highestUnlockedLevel=1`, `finaleReached=false`,
`finaleShown=false`, `lastVisitedLevel=null`, `seenExplanations=emptySet()`.
`CampaignLevelProgress` хранит `found=emptyList()`, `completedTaskIds=emptySet()`,
`hints=HintState()` и `solvedRiddleTargets=emptySet()` (угаданные цели T4).
Все сохраняемые поля имеют значения по умолчанию.
Смена слова уровня исключает старые ответы и звёзды из его прогресса и итогов,
но не уменьшает ранее достигнутую границу доступа.

`CampaignRules.stars` считает различные ID заданий текущего уровня;
`isPassed` проверяет порог R, а `isUnlocked` — сохранённую границу доступа.
Это три разных величины: открытый уровень может быть ещё не пройден, а
пройденный — иметь недобор до M. Неизвестные ID не дают звёзд.

`openLevel(campaign, progress, levelNumber, index)` принимает номер от 1,
проверяет доступ до поиска слов и восстанавливает `CurrentCampaignLevel`.
Для закрытого или отсутствующего уровня возвращает `null`: этот путь должен
использоваться и карточками, и прямыми маршрутами. Любая открытая карточка
доступна независимо от выбора «Продолжить», в том числе после 100/100.
Само открытие ничего не сбрасывает и не потребляет показ финала.

`recordLevel(campaign, progress, current)` объединяет сохранённые ответы и ID
с текущими, пересчитывает задания через `TaskRules` и возвращает новый снимок.
Вызывать после ответа и восстановления игры; сохранять весь снимок атомарно,
а следующий вызов выполнять уже с ним. Закрытый уровень, чужое описание
уровня или игра другого исходного слова отвергаются. Входные ответы — уже
принятые игрой ответы, как и у `TaskRules`; произвольный ввод здесь не проверяется.
При любых R выполненных заданиях на текущей границе следующий уровень
открывается немедленно, в том числе когда один ответ даёт две звезды.
Граница сдвигается только на следующий уровень, никогда назад; добор на
старом уровне и прохождение финального уровня её не меняют. На последнем
уровне R фиксирует `finaleReached=true` навсегда до явного сброса.

`continueLevel` до финала выбирает первый открытый уровень с числом звёзд
меньше R: недобранные дополнительные звёзды не возвращают игрока назад.
После финала выбирается первый открытый с числом звёзд меньше M, при полном
наборе — последний открытый (в полной кампании это уровень 30).

`consumeFinaleDialog` возвращает `FinalePresentation(state, showDialog)`.
UI-03 выводит ожидающий диалог из `finaleReached && !finaleShown` в потоке
сохранения, без подтверждения при открытии. `consumeFinaleDialog` используется
только при закрытии диалога: возвращённый снимок с `finaleShown=true`
сохраняется до продолжения игры или перехода на карту. До закрытия поворот
и перезапуск восстанавливают диалог; после закрытия возвраты и добор не
вызывают повторного финала. Итоги берутся из `CampaignRules.summary`.
Факт финала не означает достижения «Мастер»: `summary.isMaster` требует всех
звёзд кампании, то есть 100/100 в производственных данных. Финал 4/5 на 30-м
и даже 5/5 на нём при недоборе старых уровней этого достижения не дают.

`summary` вычисляет `stars`, `maxStars`, `passedLevels` (порог R), `totalLevels`,
`foundWords`, `shownHintSteps` и `paidHintUnits` из одного снимка сохранений
только текущих слов уровней. Найденные слова —
сумма уникальных нормализованных ответов внутри каждого уровня, включая
трёхбуквенные; одинаковый ответ на двух уровнях считается дважды.
Словарь для итогов и выбора продолжения не перебирается.

`reset()` создаёт новый `CampaignProgress`: клиент заменяет им всё сохранение
только по явному пользовательскому сбросу. Очищаются ответы, звёзды, граница
и оба признака финала, посещение и виденные пояснения; в новой кампании снова
открыт только первый уровень.
Сериализация и DataStore реализованы в SAVE-01 ниже; переключение UI v1 — отдельная задача.

## Лестница и бюджет подсказок — HINT-02

`HintRules.next(current, words=emptyMap(), countMinLength=4, random=Random.Default)`
обрабатывает один явный запрос следующей подсказки. Как и в `TaskRules`,
`countMinLength` передаётся из кампании. Возвращает `HintResult(state, step, status)`;
клиент атомарно сохраняет `state` перед показом `step`. Новый запрос выполняется
с этим снимком. Повторная доставка одного действия не должна вызывать `next`
второй раз: для восстановления экрана используются `currentStep`,
`current.hints.ladder.shown` и `budget` — они ничего не списывают и не используют
случайность. Статусы: `SHOWN`, `BUDGET_EXHAUSTED`, `NO_TARGET`, `LADDER_COMPLETE`.
У трёх последних `step=null`, нового показа и списания нет.

Выбор идёт только по местным составимым ответам `GameState.start`, без полного
перебора словаря. Найденные ответы и три запретные цели из контракта исключены;
запрет не меняет общий словарный ввод. Сначала выбирается нерешённая T4, затем
первое невыполненное задание с подходящим ответом в порядке уровня, затем
обычное слово. Выполнение учитывает и `found`, и сохранённые ID через `TaskRules`.
T1/T2 применяют минимум счётчиков, T3 использует именно назначенный `hintTarget`,
T5 — длину и окончание, T6 — местный список, T7 — наличие буквы. `HintTarget`
сохраняет слово, ID, тип и букву T2/T7. Другой ответ, закрывший это задание,
не переключает уже выбранную цель: переключение происходит после угадывания
самой цели, при следующем запросе. Показ полного ответа не добавляет его
в `found`, не выдаёт звёзд и не выбирает новую цель. После последней ступени
до угадывания возвращается `LADDER_COMPLETE`; когда ненайденных пригодных
ответов не осталось — `NO_TARGET`.

`words` — необязательная карта локальных метаданных по нормализованным словам:
`HintWordData(category, definition, forms, related, familiar, undesirableLabels)`.
Предпочтение внутри одной группы приоритета: без нежелательных помет, затем
понятные (`familiar`) слова. При отсутствии метаданных слово остаётся пригодным.
Из равных вариантов выбирает переданный `Random`; предварительная сортировка
делает seed независимым от порядка списка ответов. Метаданные поставляет клиент;
обращений к SQLite и классификации слов по тексту статьи здесь нет.

Лестница: тема → подготовленное определение → точная длина → первая буква →
шаблон с одной новой позицией за шаг → полный ответ. Пропущенные шаги не входят
в показы и расходы. `HintCategory` содержит отдельно ключ и проверяемый текст;
ключ не показывается. Небезопасная тема с ответом, его формами или родственными
словами пропускается целиком. Для темы проверка консервативнее определения:
общий префикс из трёх букв также исключает шаг. Это может пропустить полезную
тему, зато не выдаёт короткую родственную формулировку. Определение проходит
`DefinitionHint.prepare`; непригодное отсутствует в лестнице. Совпадающие тексты
темы и определения показываются один раз. Отсутствие БД оставляет буквенные шаги.

У T2 начальная позиция уже известна, у T5 известны позиции окончания, у T6
не повторяется тема с тем же ключом. Точная длина не равна нижней границе T3/T5
и остаётся отдельной ступенью. Известная буква T7 сообщает вхождение, но не
позицию: первая буква остаётся отдельным шагом, а в шаблоне сначала открывается
одна позиция буквы T7, если она ещё скрыта. Шаблон открывает **позиции**, а не все
вхождения символа; общее число известных позиций ограничено `floor(length/2)`.
Начальная буква и окончание входят в этот лимит; если они его уже достигают
или превышают, шаблона нет. Трёхбуквенное слово после первой буквы сразу
переходит к финальной ступени. До неё шаблон никогда не содержит полного слова.

`HintRules.budget` возвращает `HintBudget(initial, earned, spent)` и `remaining`.
Начальный бюджет этапов 1–6: 5, 5, 4, 4, 3, 3. Пополнение вычисляется как
`floor(число различных нормализованных found / 4)`, включая трёхбуквенные ответы;
повторные ответы и восстановление не начисляют его заново. Для цели T4 тема,
определение и длина бесплатны даже при нулевом остатке. Каждый другой
фактически показанный шаг стоит одну единицу. `HintState.shownSteps` считает
все показы за уровень, `paidUnits` — только расходы; смена цели их не сбрасывает.

`HintState.ladder` хранит `HintTarget`, подготовленный список `steps`,
`nextStepIndex` и уже известные `revealedPositions`; текущая `stage` и список
`shown` выводятся из этого снимка. Список содержит будущие ответы и не должен
отображаться целиком. Все поля сохраняемых моделей имеют значения по умолчанию.
`CampaignRules.recordLevel/openLevel` переносят снимок вместе с ответами и
звёздами; запись более старого снимка с меньшим числом показов не возвращает
бюджет. Угадывание последней цели позволяет сохранить пустую лестницу без
сброса расходов. Смена исходного слова и явный сброс создают пустой `HintState`.
При восстановлении не нужны ни повторный выбор цели, ни БД, ни прежний Random:
сохраняются тексты, порядок раскрытия и расходы. Сериализация в DataStore —
SAVE-01; подключение интерфейса остаётся отдельной задачей, клиенты v1 не переключены.

## Атомарное сохранение кампании — SAVE-01

`ProgressRepository` использует существующий `DataStore<Preferences>`.
Единственный ключ v2 — `campaignProgressV2`: JSON `CampaignProgressDto(version=2)`.
DTO и вложенные поля имеют значения по умолчанию; сериализация не затрагивает
зависимости `:core`. Неизвестные JSON-поля игнорируются. Повреждённый JSON,
неизвестная версия или неизвестные значения перечислений приводят к ошибке
чтения/события, сохраняя исходные данные; молчаливой перезаписи пустым снимком нет.
Ключи и методы v1 продолжают работать независимо до явного запуска миграции SAVE-02,
описанного ниже. События v2 запрещены при наличии v1 без снимка v2: сначала перенос.

`observeCampaignProgress()` отдаёт согласованный `Flow<CampaignProgress>`.
Итоги вычисляются `CampaignRules.summary(campaign, snapshot)` из этого же снимка,
без отдельных сохранённых сумм и объединения нескольких потоков. Последний
посещённый номер хранится отдельно от необратимой границы доступа; выбор
«Продолжить» по-прежнему задаёт `CampaignRules.continueLevel`.

Каждый вызов событийного API выполняет ровно один `dataStore.edit`:

- `submitCampaignAnswer(campaign, levelNumber, raw, index, knownWords)` внутри
  транзакции восстанавливает актуальный уровень, проверяет ответ `TaskRules.submit`
  и записывает результат через `CampaignRules.recordLevel`. Найденное слово,
  все полученные ID звёзд, решённые цели T4, открытие следующего и финал входят
  в одну запись. Повторный/отклонённый ответ не меняет снимок.
- `requestCampaignHint(campaign, levelNumber, expectedShownSteps, index, words)`
  проверяет ожидаемый монотонный счётчик показов уровня внутри транзакции.
  UI фиксирует `expectedShownSteps` из снимка в момент нажатия. Повтор того же
  события возвращает `null`, включая параллельные вызовы и перезапуск.
  Следующее отдельное нажатие использует новый счётчик. `HintRules.next`
  вычисляет цель/лестницу и расходы по актуальным ответам; состояние, включая
  будущие шаги, индекс и открытые позиции, сохраняется до возврата `HintResult`.
- `visitCampaignLevel(campaign, levelNumber)` проверяет доступ и сохраняет
  посещение без изменения границы.
- `markCampaignExplanationSeen(type)` сохраняет тип пояснения; `true` разрешает
  первый показ, `false` означает, что пояснение уже видели.
- `consumeCampaignFinaleDialog()` атомарно фиксирует `finaleShown` и возвращает
  факт первого подтверждения по `CampaignRules.consumeFinaleDialog`. UI вызывает
  метод при выборе действия или закрытии диалога, а не перед показом.

Принятое событие выполняется в `NonCancellable` на вычислительном диспетчере:
отмена UI-корутины при навигации не отменяет запись. Результат события доступен
только после успешного `edit`; ошибки записи передаются вызывающему коду.
UI показывает подтверждённые ответы/шаги/пояснения после успешного вызова,
при возврате использует сохранённый снимок и `HintRules.currentStep`.
Защита не заменяет долговременную очередь при завершении процесса до записи.
`clearAll()` одной транзакцией удаляет все ключи прогресса v1 и v2, включая
расходы, пояснения, посещение и признаки финала.

`CampaignProgressRepositoryTest` проверяет реальный файловый DataStore через
`OkioStorage`: повторное открытие, два уровня, согласованность Flow при 100
конкурентных ответах от двух экземпляров репозитория, конкуренцию ответа и
платной подсказки, повтор событий, сбой до коммита, отмену UI во время записи,
поля по умолчанию, совместимость v1, защиту неизвестной версии и полный сброс.
Барьер и ошибка в тестовом адаптере `updateData` находятся после вычисления
изменения и до подтверждения записи; задержек по времени и сети нет.

## Перенос сохранений — SAVE-02

После загрузки **настоящей кампании v2** и актуального `WordIndex` клиент вызывает
`ProgressRepository.migrateCampaign(campaign, index)` до событий v2. Чтение через
старые наблюдатели, `observeCampaignProgress()` и временный адаптер v1 не запускают
миграцию. Загрузка кампании и переключение UI остаются отдельными задачами;
`AppContainer` по-прежнему обслуживает UI v1 и автоматически перенос не начинает.
Нужна непустая кампания версии 2 с номерами 1..N и уникальными каноническими
исходниками. Метод возвращает только подтверждённый сохранённый снимок.

Один `DataStore.edit` читает **фактические** ключи `currentGame`, `levelProgress`,
`levelAnswers`, записывает `campaignProgressV2` и удаляет все три старых ключа.
Вычисление идёт вне UI-потока, принятая транзакция защищена `NonCancellable`.
Сбой записи оставляет все старые ключи; повторный вызов или перезапуск безопасен.
Если v2 уже существует, он имеет приоритет: метод проверяет формат и возвращает
его без пересчёта, повторной выдачи звёзд и удаления поздних записей v1.
Необрабатываемый JSON, `null`, неизвестная версия v1/v2 и неизвестные перечисления
дают ошибку без перезаписи или удаления. Отсутствующие необязательные поля v1
получают прежние значения по умолчанию, включая пустой `currentGame.found`.

`LegacyCampaignV1.kt` фиксирует только слова и порядок 30 поставленных уровней
из `data/levels.json` с SHA-256
`e4ded7a9bdfc5855c69bd167abb03c25d5291652a1504956d3a0e99e4742e73a`.
Карта входит в код приложения и не зависит от текущих assets, генератора,
кэшей или наличия старых файлов на устройстве после обновления. Менять её при
генерации кампании нельзя. Числовые пороги v1 для переноса не нужны.

Сопоставление записей идёт по `Alphabet.normalize(source)` и только по исходникам
этой исторической карты, сохранившимся в v2, независимо от смены номера. Ответы
из нормализованных ключей объединяются, нормализуются и фильтруются
`GameState.start` по актуальному словарю и мультимножеству букв; повторы, исходное
слово и ответы короче трёх букв отсеиваются. Старые `completed`, `wordsTask`,
`lettersTask` не превращаются в ID заданий v2. `TaskRules.evaluate` заново считает
все задания по допустимым ответам с новым `countMinLength`; сохраняются и найденные
цели T4. История/расходы подсказок и просмотренные пояснения начинаются с нуля.
Заменённое или удалённое слово не отдаёт ответы и звёзды новому слову на его месте.

Граница доступа — максимальный номер, открытый по `completed` предшественника
в **старом порядке**, ограниченный сначала 30 уровнями v1, затем длиной v2.
Даже удалённый исходник сохраняет достигнутую границу. Прочие старые флаги,
наличие ответов и вновь вычисленные звёзды не открывают дополнительные уровни.
Пересчёт не вызывает `CampaignRules.recordLevel`: нет цепочки открытий или
автоматического финала. `lastVisitedLevel=null`, оба признака финала — `false`;
старый флаг не объявляет кампанию v2 или добор всех звёзд завершёнными.

У `currentGame` v1 нет режима и номера. Его ответы подхватываются только при
уникальном совпадении исходника с реальным уровнем **обеих** кампаний и наличии
отдельной записи того же нормализованного слова в `levelProgress` либо
`levelAnswers`. Запись только `currentGame` неоднозначна даже при совпадении слова:
она могла быть свободной игрой. Она не создаёт чужого прогресса. Несовпадающая
свободная игра также не переносится; после успешной миграции старый ключ удаляется.
`clearAll()` очищает обе версии, даже если одна из них не читается.

`LegacyCampaignMigrationTest` проверяет эти случаи на реальном файловом DataStore,
включая перестановку, удаление, замену, неполные поля, одни флаги, свободную игру,
неоднозначность, битый JSON, будущие версии, повтор после перезапуска, конкуренцию
двух репозиториев, сбой перед коммитом и отмену UI при принятой записи.

## Объяснения отказа — CORE-04

`GameState.submit(raw, index=null, knownWords=null)` сохраняет прежний порядок
проверок: EMPTY → TOO_SHORT → SAME_AS_SOURCE → ALREADY_FOUND → точный CORRECT.
Только точное множество `allWords` разрешает зачёт. Затем проверяется точное
наличие в переданном `WordIndex`, а при его отсутствии — `KnownWords.mightContain`.
Справочники передаются при отправке ответа и не входят в сохраняемое состояние.
Без них действует прежний NOT_FOUND; подключение фильтра и новых сообщений
в Android остаётся отдельной задачей.

Для распознанного слова проверяется мультимножество букв исходника.
LETTERS_MISSING сопровождается `Submission.missingLetter: MissingLetter`:
`letter`, `available`, `required`. Возвращается первая нехватка в порядке
`Alphabet.LETTERS` после нормализации ё→е, количества относятся ко всему слову.
Если букв хватает, но точного ответа нет, возвращается NOT_COUNTED.
Нераспознанное слово даёт NOT_FOUND независимо от букв.

`Submission.probabilistic=true` только для двух объяснений, основанных исключительно
на Bloom. Это признак для формулировки сообщения, а не разрешение на зачёт;
ложноположительный фильтр может изменить лишь объяснение отказа.
Точное наличие в `WordIndex` имеет приоритет над вероятностным справочником.
У ранних результатов и CORRECT признак false, `missingLetter=null`.

`TaskRules.submit` принимает те же необязательные справочники после
`countMinLength` и передаёт детали отказа через `TaskSubmission`.
Любой отказ возвращает прежний GameState и прежний CurrentCampaignLevel,
пустой `newlyCompletedTaskIds`; не меняются found, сохранённые звёзды,
подсказки, бюджет и статистика. Даже если found уже выполняет задание без
сохранённого ID, отказ не согласовывает его в новую звезду: для восстановления
по-прежнему есть явный `TaskRules.evaluate`.

## Валидация и границы моделей

В моделях нет локализованных названий этапов, типов и тем, определений и
текстов интерфейса. Для локализации используются ключи `Stage.number`,
`TaskType`, `T6.category`; русский UI хранит подписи отдельно в ресурсах.
Наличие списка `T6.words` позволяет проверять тему без базы определений.

`CampaignValidator.validate` возвращает список `CampaignValidationError`:
`field`, диагностическая `reason`, `levelNumber`, `taskId`. Для ошибок задания
оба адреса заполнены; для ошибок уровня ID отсутствует, для общих ошибок
нет номера уровня. Пример: `level=1 task=l1-count n: Must be positive`.
Причины предназначены разработчику, не для показа в интерфейсе.

Проверяются версия, минимум счётчиков, непустая кампания, уникальные этапы и
неперекрывающиеся диапазоны, последовательные номера уровней от 1, уникальные
слова и ID, ссылки на этапы, M в 1..5, R в 1..M, разные типы внутри уровня,
границы параметров и непустые списки. Слова и буквы должны уже соответствовать
`Alphabet` (нижний регистр, ё→е, без посторонних символов). Данные отвергаются,
а не исправляются молча. Явные цели и тематические ответы проверяются на
составимость через `WordIndex`, включая кратность букв и исключение исходника.
Цели T3/T4 уникальны в общем нормализованном пространстве, окончания T5 и
ключи тем T6 — во всей кампании. Обычные ответы и буквы T2/T7 могут повторяться.

`ProductionCampaignValidator.validate` дополнительно требует 30 уровней,
6 этапов по 5, максимум 100 звёзд, расписание типов и M/R из контракта,
ротацию последних пяти уровней с появлением T6/T7. Структурный валидатор
работает на мини-кампаниях без этих производственных ограничений.
Проверка словарного членства, полноты тематического списка, достижимости
неявных ответов, качества контента и запасов генератора не подменяется
структурной проверкой и относится к проверке сгенерированного пакета.

JSON разбирается существующими средствами на границе `:app`: декодер должен
проверить типы JSON-полей, обязательные параметры и неизвестные типы заданий,
создать соответствующий подкласс `CampaignTask`, затем вызвать валидатор.
В этой задаче клиенты ещё не переключаются на v2; JSON-парсер не добавляется.
Android, сериализация и runtime-зависимость от `org.json` в `:core` не нужны.
