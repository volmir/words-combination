## Точный формат хранения

Файл во внутреннем каталоге приложения:
`files/datastore/play_time.preferences_pb`. Это стандартный protobuf Preferences
DataStore, значения записей — строки JSON с `encodeDefaults=true`.

Ключ каждой записи:

```text
playTimeV1:<64 строчных hex-символа SHA-256 campaign.json>:<номер уровня>:<исходное слово>
```

SHA берётся из `Campaign.contentSha256`: существующий `LevelsRepository` вычисляет
его по содержимому установленного asset и в production сверяет с BuildConfig.
Пустая/неверная идентичность запрещена. Уровень выбирается по номеру из этой
кампании. Другой SHA, номер или слово означают отдельную запись. Архивные записи
не удаляются и не суммируются с текущей кампанией, в Flow попадают только её уровни.

Пример JSON после первого сегмента 120 мс и достижения R=2 из M=5:

```json
{"cumulativeActiveMs":120,"timeToRMs":120,"timeToFullMs":null,"initialized":true,"rAccounted":true,"fullAccounted":false,"lastSequence":1,"lastStars":2,"version":1}
```

Все миллисекунды и номера сегментов — `Long`. Количество звёзд — `Int`.
Отсутствующая запись читается как `LevelPlayTime()` (0 мс, оба времени `null`,
`initialized=false`, оба accounted=false, sequence=0, stars=0, version=1).
Чтение не создаёт запись на диске.

`initialize(campaign, levelNumber, starsBeforeTracking)` обязателен до сегментов.
Уже пройденные пороги отмечаются accounted=true при времени null. Повторная
инициализация не меняет baseline. Таким образом, исторические звёзды не становятся
рекордами 0 мс. Сегмент 0 мс допустим, в том числе для настоящего перехода порога
после инициализации таймера. Достигнутый порог фиксируется один раз в конце сегмента;
одновременное достижение R и M даёт одинаковое время. Накопление продолжается после M.

## API, атомарность и ошибки

- `observe(campaign)` — Flow карты `номер -> LevelPlayTime`, в порядке уровней
  кампании; `snapshot(campaign)` — первый актуальный снимок того же потока.
- `appendSegment(campaign, levelNumber, sequence, activeMs, starsAfter)` — одна
  транзакция DataStore для суммы, обоих порогов и номера события. Реальные звёзды
  передаёт вызывающий код из :core; репозиторий их не вычисляет и не меняет.
- Сегменты нумеруются 1, 2, ... отдельно для каждого ключа, с продолжением от
  сохранённого lastSequence после перезапуска. Повтор любого уже принятого номера
  ничего не меняет. Пропуски запрещены. Вызывающий код должен сериализовать разные
  сегменты одного уровня и при ошибке повторять **исходные аргументы** с тем же
  номером; более поздний сегмент нельзя выдавать за повтор старого события.
- DataStore сериализует транзакции даже для нескольких репозиториев над одним
  экземпляром DataStore. Отдельный mutex не нужен. Suspend-запись завершается после
  сохранения; future lifecycle-код должен дождаться её завершения. Барьер
  `ProgressRepository.awaitSaved()` обслуживает только существующий прогресс.
- Отрицательные длительности, недопустимые звёзды, уменьшение числа звёзд,
  неизвестные уровни и номера событий запрещены. `Math.addExact` не допускает
  переполнения: вся транзакция отклоняется без изменения записи.
- Повреждённый protobuf/JSON, неподдерживаемая версия и нарушенные инварианты
  вызывают ошибку чтения/записи. Никакого автоматического обнуления, замены
  повреждённого файла или выдачи ложного успешного результата нет.
- `clearTimeStatistics()` явно очищает только отдельный файл времени, включая
  прежние кампании. В игровом UI вызовов нет. При нечитаемом protobuf ошибка
  DataStore также передаётся вызывающему коду; тихое восстановление не добавлено.

Выбран отдельный DataStore, чтобы не вмешиваться в существующие writeMutex,
повторы операций и awaitSaved игрового прогресса. Существующие сохранения остаются
побайтно независимыми. Сброс ProgressRepository также не очищает время.
Новых зависимостей, разрешений, сетевых вызовов, персональных данных нет.
