# Действующий процесс выпуска и обновления F-Droid

Этот порядок введён FDROID-RELEASE-111. Исторические отчёты
[FDROID_REPRO_02.md](FDROID_REPRO_02.md) и
[FDROID_FIX_110_REPORT.md](FDROID_FIX_110_REPORT.md) сохраняют прежние результаты,
но не задают процесс нового выпуска. Итоги 1.1.1 — в
[FDROID_RELEASE_111_REPORT.md](fdroiddata/FDROID_RELEASE_111_REPORT.md).

## Подготовка исходников

Каждая публикация требует разрешения владельца на конкретную версию.
Не заменять существующие APK, не перемещать опубликованные теги, не выпускать
следующий номер как обход ошибки. Сохранять историю и пользовательские изменения.
Функциональная основа технического выпуска определяется явно; текущее состояние
`main` не подставляется автоматически. Разрешена отдельная релизная ветка.

До создания тега проверить versionName/versionCode во всех актуальных местах,
Fastlane changelog соответствующего кода и отсутствие лишних изменений в
`app/src`, `core`, `data`, `legal`. Версии инструментов не повышать без причины.
Для 1.1.1 использованы JDK Temurin 21.0.13, Gradle 9.3.1, AGP 9.1.1,
Kotlin 2.2.10, SDK android-36, Build Tools 36.0.0 и R8 9.1.31.

Выполнить gates проекта, включая Python/оркестратор, документацию, приватность,
`:core:cleanTest :core:test :app:assembleDebug` и release-сборку. Не выдавать
`UP-TO-DATE` за повторное выполнение тестов. Проверить обновление с предыдущего
подписанного APK без удаления прогресса; если оно не выполнялось, записать NOT_RUN.
Проверки прав и лицензий обязательны; технический выпуск не даёт новых прав.

Создать окончательный коммит и новый локальный аннотированный тег. Сверить его
полный SHA. Уже существующий тег не переназначать. Исходники для этого выпуска
после публикации тега не менять. Последующие отчёты оформлять отдельным коммитом.

## Два чистых APK и подпись

Нужны `git`, Bash, JDK 21, Android SDK, Python, `apksigner`, `apksigcopier`.
Кеш загруженных зависимостей допускается; build outputs проекта не переносятся.
Штатный скрипт работает offline, поэтому зависимости должны быть уже загружены.

Четыре `SOSTAVSLOVA_RELEASE_*` переменные настраиваются безопасно только в
окружении владельца согласно [RELEASE_SIGNING.md](RELEASE_SIGNING.md).
Не печатать окружение, пароли или содержимое локального `keystore.properties`.
Не переносить ключ и переменные подписи в F-Droid/CI. Новый ключ не создавать.

Переменные ниже означают уже согласованный выпуск и новый каталог экспорта:

```bash
python3 tools/prepare_verified_release.py \
  --tag "$RELEASE_TAG" \
  --expected-version-code "$RELEASE_CODE" \
  --output-dir "$VERIFIED_RELEASE_DIR"
```

Скрипт получает исходники тега в двух независимых полных Git-клонах по разным
абсолютным путям. Рабочий каталог приложения не является источником готового
APK. Оба клона не получают секретов или локального `keystore.properties`;
используются `--no-build-cache --no-daemon`. Сам Gradle проверяет JDK 21 и
печатает фактические java.version/vendor/home из своего процесса.

После двух release-сборок проверяются версии, Git revision APK и полные SHA-256
неподписанных файлов. При несовпадении подпись и экспорт запрещены. Только затем
один из сравнённых файлов подписывается существующим ключом через `apksigner`;
пароли передаются через окружение. Новая Gradle-сборка после сравнения не нужна.
Второй APK проверяется переносом подписи через `apksigcopier`, включая проверку
v2-подписи и точного сертификата владельца. При ошибке экспорт не создаётся.

Проверенный экспорт содержит именной APK, `SHA256SUMS.txt`, два `unsigned-*.apk`
и `reproducibility-evidence.json`. Наличие обычного
`app/build/outputs/apk/release/app-release.apk` не даёт права публиковать его.
`:app:prepareGithubRelease` только проверяет существующее свидетельство;
самостоятельную сборку и проверку публичного скачивания он не заменяет.

## Публикация и проверка публичных байтов

До публикации проверить поддержку `gh release create --verify-tag` установленным
GitHub CLI. В FDROID-RELEASE-111 использован официальный CLI 2.105.0; старый
CLI 2.4.0 не поддерживал этот флаг. Ключи авторизации не выводить.

Отправить проверенные ветку и тег без force-push. Для публикации использовать
только штатный скрипт и явный каталог проверенного экспорта:

```bash
python3 tools/publish_verified_release.py \
  --verified-dir "$VERIFIED_RELEASE_DIR" \
  --github-repo "$RELEASE_REPOSITORY"

python3 tools/publish_verified_release.py \
  --verified-dir "$VERIFIED_RELEASE_DIR" \
  --github-repo "$RELEASE_REPOSITORY" --publish
```

Первый запуск выполняет локальную проверку без публикации. Второй фиксирует
копию экспорта, проверяет Git-коммит, состояние свидетельства, сертификат,
оба неподписанных SHA, revision и SHA выбранного APK. Затем повторяется
криптографическая проверка. Выбор файла из обычных Gradle outputs запрещён;
несовпадение файла со свидетельством прекращает публикацию.

Публичный тег должен совпадать со свидетельством. Существующий релиз/артефакт
не заменяется. Описание различает локальную проверку и независимую проверку
F-Droid. После загрузки скрипт скачивает APK по публичному URL, сравнивает его
SHA-256 с проверенным подписанным файлом и повторяет `apksigcopier` относительно
сохранённого независимого APK. Итог — `publication-verification.json`.

При ошибке публичного скачивания или несовпадении записать FAIL и остановиться.
Не обновлять MR, не объявлять релиз корректным, не перезаписывать его. Нужен
отдельный разбор и решение владельца. Результаты предыдущего релиза не служат
доказательством нового.

## Существующий MR !58000

Рабочая копия fdroiddata:
`/var/www/fdroiddata-words-combination-mr58000`, ветка `new-app-wordscombination`.
Источник актуальной конфигурации — YAML именно в этом репозитории и существующем
[MR !58000](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/58000).
Копия [metadata](fdroiddata/metadata/io.github.volmir.wordscombination.yml)
в приложении только синхронизируется после проверки; устаревший локальный шаблон
не должен заменять принятый рецепт.

Сохранять `AutoUpdateMode: Version`, `UpdateCheckMode: Tags`, `Binaries`,
`AllowedAPKSigningKeys`, стандартное `gradle: yes` и полный SHA приложения.
`data/word_sources.jsonl.gz` нужен проверкам лицензий и копированию assets:
оставлять узкий `scanignore`, не удалять provenance через `scandelete`.
Не отключать проверки лицензирования. Исключения QA должны быть точными и
относиться только к существующим неиспользуемым архивам.

По замечанию ревьювера от 2026-11-25 buildserver F-Droid уже использует JDK 21.
В актуальном рецепте нет установки Java через `sudo` и изменения
`org.gradle.java.home` через `prebuild`. Не возвращать эти команды из старых
отчётов. При локальной проверке выбрать установленный JDK 21 через `JAVA_HOME`
и `PATH` до запуска F-Droid; подтвердить JVM в журнале процесса Gradle.
Персональные пути не добавлять в проверяемые публикационные файлы.

Описания берутся из Fastlane релизного коммита; отдельный `en-US/summary.txt`
в fdroiddata удалён как дубликат. `MaintainerNotes` удалён по просьбе ревьювера;
доказательства происхождения словаря и воспроизводимости сохранены в исходниках
и отчётах проекта.

Эти правила применяются и к следующим обновлениям нашей заявки:

- Не возвращать `MaintainerNotes`, `sudo` и `prebuild` из прежних рецептов.
  Установка JDK и изменение Java через рецепт не нужны в проверенном buildserver.
- Не дублировать тексты Fastlane полями `Name`, `Summary`, `Description` в YAML
  или локализованным `summary.txt` рядом с ним. Проверить Fastlane именно
  релизного коммита, затем Changes MR: для текущей заявки должен оставаться
  только YAML приложения.
- Сохранить источник актуального YAML в fdroiddata; синхронизировать внутреннюю
  копию после исправлений, а не восстанавливать удалённые поля по старым отчётам.

Основание — [замечание об описании и MaintainerNotes](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/58000#note_4318364838)
и [замечание о Java](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/58000#note_4318400300).
Это согласованные решения для данного проекта, не общий запрет полей схемы
F-Droid. Если окружение изменится и возникнет подтверждённая необходимость,
обновить рецепт, техническое обоснование, эти инструкции и регрессионные проверки
вместе; не обходить валидатор ради прохождения проверки.

Локальная предварительная проверка `python3 tools/check_fdroid_submission_candidate.py`
читает версию, versionCode и полный commit из текущего YAML, сопоставляет их
с исходниками соответствующего Git-тега и проверяет согласованные защитные
параметры. Он отклоняет перечисленные выше поля и дублирующий `summary.txt`
во всех локализациях рядом с выбранным YAML. Старой привязки к 1.0.2 /
AutoUpdateMode None нет. Это статическая
проверка без публикации; она не заменяет fdroid lint, scanner, checkupdates,
сборку, сравнение APK и решение сопровождающего.

Из корня приложения проверить и копию, и реальный файл существующего MR:

```bash
python3 tools/check_fdroid_submission_candidate.py
python3 tools/check_fdroid_submission_candidate.py --metadata /var/www/fdroiddata-words-combination-mr58000/metadata/io.github.volmir.wordscombination.yml
```

Первая команда не видит файлы из другого репозитория. Вторая проверяет YAML
и соседние локализованные summary в реальном fdroiddata; поэтому успешной
проверки одной копии недостаточно. Свежие тесты защиты от возврата удалённых
настроек: `python3 -m unittest tools.tests.test_fdroid_submission_candidate`.

Перед проверками согласовать fdroidserver и YAML-библиотеку с CI. Для текущего
pipeline использованы fdroidserver `fc2c86473e66a44fc641f403c338a8b2cccfad88`
и ruamel.yaml 0.18.10 из окружения Debian trixie. Результаты проверять по выводу
и APK: exit code команды сам по себе может не отражать неудачную сборку.

Команды выполняются **последовательно**: `checkupdates`, `scanner` и `build`
используют один `fdroiddata/build` и не должны работать одновременно.

```bash
cd /var/www/fdroiddata-words-combination-mr58000
fdroid rewritemeta io.github.volmir.wordscombination
fdroid lint io.github.volmir.wordscombination
fdroid checkupdates --auto io.github.volmir.wordscombination
fdroid scanner --exit-code "io.github.volmir.wordscombination:$RELEASE_CODE"
fdroid build -v -l --test "io.github.volmir.wordscombination:$RELEASE_CODE"
```

До коммита `checkupdates` допускает штатный `--allow-dirty`. После коммита
повторить без него. Повторный `rewritemeta` и `checkupdates` не должны менять
YAML. Явно сравнить APK из `fdroiddata/tmp` с публичным APK через `apksigcopier`.
Не ограничиваться обычной Gradle-сборкой и не обходить scanner/CI.

Перед push проверить diff, ветку, remotes и отсутствие посторонних изменений.
Один логически завершённый коммит отправляется в существующую ветку MR.
Описание MR и каждый чекбокс обновляются отдельно через API, затем читаются
повторно. Сохранить заголовок `New app: Words Combination`. Не создавать другой
MR и не выполнять merge. Сверять все пункты актуального шаблона, включая N/A;
не удалять неудобные пункты. CI и Reports отмечать только для текущего коммита.

После CI получить все обязательные jobs и реальные Reports, подтвердить
независимый перенос подписи. Вопрос Inclusion Policy, включая три месяца активной
разработки и возможные исключения, требует отдельных фактов и решения
сопровождающего. Успешная сборка не означает принятия приложения в каталог.
