# RIGHTS-02 — две независимые фазы проверки подсказок

Технический протокол не заменяет ручную оценку качества, оригинальности,
корректности и отсутствия раскрытия ответа. Он не удостоверяет личность автора
файла. Доверенная граница — документы, действительно заполненные владельцем
и человеком, проводящим полный аудит. Агент не вправе заполнять их вместо людей.
Проверка SHA подтверждает соответствие байтам, а не происхождение прав.

## Состояния

| Свидетельства | Лицензия в БД/manifest | audit / rights_review | publication_status | Release |
|---|---|---|---|---|
| Акта нет или он в точности соответствует неподписанному акту pending | Плейсхолдер | false / false; pending-owner-approval | draft-not-for-public-release | Запрещён |
| Валидный акт; отдельного полного аудита ещё нет | CC0-1.0 | false / false; pending-manual-audit | draft-not-for-public-release | Запрещён |
| Валидный акт и отдельный полный ручной аудит текущей БД | CC0-1.0 | true / true; approved | approved | Ворота подсказок пройдены |
| Неверный/устаревший акт, аудит либо противоречивый manifest | — | Проверка завершается ошибкой | — | Запрещён |

`approved` означает прохождение только этих ворот. Разрешение публикации,
права на прочие материалы, подпись и остальные критерии релиза остаются
отдельными решениями/проверками. Исторический выбор процесса и waiver не
являются актом утверждения. Для собственных подсказок
`--allow-unaudited-release` не разрешает сборку release; Gradle не передаёт его
даже при установленном старом свойстве `sostavslova.release.allowUnauditedDefinitions`.

## Фаза 1: решение владельца

Только владелец самостоятельно создаёт `docs/OWN_HINTS_OWNER_APPROVAL.json`
по схеме [RIGHTS-01](OWN_HINTS_OWNER_APPROVAL.template.json), после проверки
[пакета всех 39 текстов](OWN_HINTS_OWNER_REVIEW.md). Сборщики этот файл только
читают. CLI для записи акта или подстановки иной лицензии нет.

Требуются точные schema/version/path, `decision="approved"`, четыре булевых
подтверждения `true`, календарная дата `approved_on` в формате `YYYY-MM-DD`,
`license="CC0-1.0"`, counts 39/40 и SHA-256 реальных байтов кандидата и кампании.
Число `1` не принимается за `true`, `39.0` не принимается за `39`.
Лишние и повторяющиеся поля, частичные подтверждения, пустые/невалидные даты
и несовпадение SHA приводят к ошибке. Только точная неподписанная форма с
`decision="pending"`, четырьмя `false` и `approved_on=null` остаётся PENDING.
Сам файл `.template.json` не считается актом и никогда не используется вместо него.

`docs/owned_hints.json` остаётся неизменным авторским снимком с историческими
pending-полями. Для APPROVED их не редактируют: решение привязано к SHA всего
этого файла. Установщик меняет только служебные метаданные лицензии и SHA
акта в SQLite; тексты, строки definitions и word_metadata остаются прежними.

После действительного акта обычный `python3 tools/build_owned_hints.py`
устанавливает воспроизводимую БД с проверенной лицензией, но ещё с обоими
флагами `false`. Человек проверяет именно эту итоговую БД.

## Фаза 2: отдельный полный ручной аудит

Человек отдельно создаёт `docs/OWN_HINTS_MANUAL_AUDIT.json`. Этот файл не
создаётся инструментами сборки, шаблон с проставленными PASS не генерируется.
Здесь описана схема, а не результат выполненного аудита:

| Поле | Обязательное значение |
|---|---|
| schema / version | `owned-hints-human-audit` / целое `1` |
| reviewer | Непустое имя проверявшего человека |
| reviewed_on | Календарная дата `YYYY-MM-DD`, не раньше approved_on |
| candidate_sha256 | SHA-256 байтов `docs/owned_hints.json` |
| campaign_sha256 | SHA-256 байтов `data/campaign.json` |
| owner_approval_sha256 | SHA-256 байтов действительного акта владельца |
| database_sha256 | SHA-256 итоговой `data/definitions.db`, уже с метаданными фазы 1 |
| checked / bad | Целые `39` / `0` |
| entries | Все 39 записей в порядке entries кандидата; без пропусков/дубликатов |

Каждая запись `entries` содержит строго поля:

- `word`: точное слово кандидата;
- `hint_sha256`: SHA-256 UTF-8 текста `hint`, без добавленного перевода строки;
- `quality`, `originality`, `correctness`, `no_answer_leak`: каждое равно строке
  `"pass"` только после соответствующей ручной проверки текста.

Неизвестные поля, булево `passed` вместо полного отчёта, 38 проверок,
любая проблема или несовпадающий хэш запрещают переход. Аудит без решения
владельца также считается противоречивым. Автоматическое совпадение JSON
не является фактом проведения аудита: ответственность за его содержимое
остаётся у указанного человека. Проверку чужих текстов моделью не выполняют.

После ручного заполнения повторный `python3 tools/build_owned_hints.py`
сверяет отчёт с воспроизведённой БД и записывает производные флаги и SHA отчёта
в manifest. Аудит не входит в SQLite, поэтому циклического хэша БД нет.
Повторная установка сохраняет подтверждённое состояние побайтно.

`python3 tools/build_owned_hints.py --check` и release-ворота заново читают
оба свидетельства и сравнивают весь definitions-блок manifest с ожидаемым.
База дополнительно сверяется побайтно со свежей сборкой: пересчёт SHA
подменённой БД или добавление Wiktionary-строки не обходят проверку.
Свежая сборка использует [закреплённую SQLite](OWN_HINTS_TOOLCHAIN.md).
Отсутствующий утверждённый артефакт восстанавливается из закреплённого
Git-коммита с проверкой SHA; для экспорта без Git предусмотрена отдельная
подготовка с явным `--download`. Существующая БД и свидетельства при этом
не заменяются.
Удаление свидетельства либо изменение даже пробелов кандидата, кампании
или акта аннулирует прежнюю привязку. Изменённый кандидат также требует
новой проверки происхождения/лексического индекса по существующему процессу.

## Реальное состояние после RIGHTS-02

Реальный акт и реальный ручной аудит не созданы. Кандидат, кампания, БД и
manifest не изменены; `audit.passed=false`, `rights_review.passed=false`.
Временные синтетические фикстуры доказывают техническую достижимость
APPROVED и отказы при подменах, не выражая решения владельца.
