# Измеримые профили исходников — GEN-01

`tools/pick_level_words.py` измеряет существительные 8–13 букв из подготовленного
словаря и три предпочтительных исходника владельца. Кампанию и задания он не
назначает, файлы `data/` не записывает. Все операции локальные, зависимостей и
сетевого транспорта нет.

## Входы и отбор

Обязательны текущие `data/words.txt`, манифест, БД определений, локальный дамп,
проверенный список FREQ-01 и зафиксированный исходный частотный универсум.
По умолчанию универсум читается из
`tools/cache/cleanup/source-vocabulary-<sha256 дампа>.json`; его состав сверяется
с `manifest.selection.input_words_sha256`. Можно передать тот же набор через
`--frequency-universe` как JSON-снимок либо текстовый список. Ранги вычисляются
среди исходных 113 413 слов, а не только оставшихся в игровом словаре.
Частоты суммируются по уникальным нормализованным словоформам существующих
инструментов FREQ-01; ё/е объединяются, омонимия форм не разрешается.

Лексические признаки и роли заново извлекаются текущим LEX-01 из дампа.
Дополнительный проход сохраняет закрытые пометы historical/religious/derived_feminine
из структурированных тегов, чтобы их свёртка в restricted_usage не разрешила
обход религиозной пометы для предпочтительного исходника.
Старые исключения сохранённых уровней не делают слово пригодным для v2.
Категории по умолчанию вычисляются локальными правилами LEX-02, с проверкой
всех доступных значений. `other` и неизвестность темой задания не становятся.
Актуальный `--categories category_index.json` LEX-03 может дополнить этот вход;
проверяются словарь, БД, покрытие и закрытая таксономия.

Граница LEX-04 экспортируется в `suitability_input.json`: только слова, роли,
булевы признаки, пометы, наблюдаемые частоты и ранги. Тексты определений,
источники и статьи в этот файл не попадают. Достижимость здесь предварительная:
для исходника есть хотя бы один составимый ответ 4+, для цели — хотя бы один
составимый исходник из измеряемых существительных. Это ещё не проверка
достижимости набора заданий кампании.

Для узнаваемых ответов требуется минимум 10 наблюдений **и** положительная
пригодность target по LEX-04. Нейтральные частотные слова проходят его дешёвое
правило; остальные требуют актуального результата ИИ. Отсутствие снимка и
`insufficient_data` дают консервативный `pending`, исключённый из назначений.
`--suitability word_suitability.json` принимает результат LEX-04 только для
точного экспортированного входа; проверяет признаки, полноту, ID, версию и хэши,
заново применяет жёсткие правила. Генератор профилей сам модель не вызывает.

Наблюдаемая частота не является оценкой ИИ. Ноль означает **«не наблюдалось
в этом корпусе»**. Частота, статус наблюдения, источник семантической оценки,
её решение, причина и версия хранятся раздельно. Исторические, религиозные,
жаргонные, производные феминитивы, сокращения и уменьшительные учитываются
лексическими правилами и пометами LEX-04. Продуктивные уменьшительные не
назначаются; лексикализованные ручка/ножка/рыбка сохраняют политику владельца.

Прелюбодейка, брудершафт, праймериз не получают профилей исходников,
назначенных целей и подсказок. Общие допустимые ответы по словарю сохраняются.
Хлопкопункт, реввоенсовет, селитроварня могут обходить порог частоты и
закрытый набор ограничительных помет LEX-04 **только в роли исходника**.
Применение обхода записывается в профиле. Их ответы и цели проходят общие
проверки. `source_eligible` дополнительно требует узнаваемый ответ 4+;
окончательную достижимость всех заданий проверит отдельный генератор кампании.

Все настраиваемые числовые пороги, единицы и обоснования — в
`tools/level_profile_config.json`. Границы 8–13, 3, 4 и пороги дешёвого правила
LEX-04 проверяются на соответствие контрактам, не подменяются молча.

## Подсказки из реальной БД

Используется непосредственно результат `core/DefinitionHint` + `HintText`
через существующий `DefinitionHintDatasetAudit`. Python-порт не определяет
пригодность загадки, поэтому сравнительный прогон порта не требуется.
Экспорт включает полные определения в порядке БД, формы и ближайшее родство.
Поле `guessable` не читается, в том числе его исходные нули. Для трёх запретов
владельца экспортируются пустые списки определений.

```sh
python3 tools/pick_level_words.py \
  --export-hints build/reports/level_profiles/hint_inputs.jsonl
bash gradlew :core:auditDefinitionHints \
  --args='../build/reports/level_profiles/hint_inputs.jsonl ../build/reports/level_profiles/hints.jvm.jsonl' \
  --console=plain
python3 tools/pick_level_words.py
```

JVM сохраняет заголовок экспорта. Профили проверяют хэши БД, словаря,
актуальных исходников обоих обработчиков и экспортёра, версии, полное
покрытие слов и отсутствие дублей. Старый экспорт после изменения кода
отвергается. В кэше профилей остаются только булева пригодность и хэш подсказки;
тексты статей туда не копируются. `riddle_targets` — пересечение узнаваемых
назначаемых целей и пригодных JVM-подсказок, а не все слова с определением.

## Семантический снимок

Сначала можно подготовить признаки без JVM-результата:

```sh
python3 tools/pick_level_words.py --prepare-only
```

Полученный `build/reports/level_profiles/suitability_input.json` передаётся
существующему LEX-04 по [его инструкции](WORD_SUITABILITY.md). Затем:

```sh
python3 tools/pick_level_words.py \
  --suitability build/reports/suitability/word_suitability.json
```

Если используется отдельный индекс категорий, передавайте один и тот же
`--categories` на подготовке и основном прогоне. Смена влияющих признаков
требует нового снимка LEX-04. Незавершённый снимок допустим как явно неполный:
неподтверждённые слова не получают разрешения на назначение.

## Схема профиля и кэш

Поиск идёт по trie отсортированных мультимножеств букв; одинаковые сигнатуры
сохраняют все анаграммы. Исходник исключается после нормализации, минимальный
общий ответ — 3 буквы. Повторяющиеся буквы расходуются поштучно.

`tools/cache/level_profiles/<ключ>.json.gz` содержит общую таблицу слов
(`observed_frequency`, noun, пометы, категория и её источник), оценки обеих
ролей, пригодность подсказок и таблицу `profiles` по нормализованному исходнику.

| Поле профиля | Смысл |
|---|---|
| `answers` | Все составимые ответы словаря от 3 букв |
| `recognizable_answers` | Подтверждённо пригодные цели с наблюдаемой частотой не ниже порога |
| `assigned_targets` | Пул целей до назначения уникальности кампанией |
| `riddle_targets` | Пригодные загадки после JVM-обработки |
| `all`, `recognizable` | Два независимых набора метрик |
| `*.count`, `*.count_4plus` | Все ответы и отдельно ответы 4+ |
| `*.lengths` | Количество по точной длине |
| `*.initial`, `*.initial_4plus` | Количество по начальной букве |
| `*.containing`, `*.containing_4plus` | Количество слов, содержащих букву; повтор буквы в слове не увеличивает счётчик |
| `*.suffix_lengths` | Окончание → точная длина ответа → количество; совместная достижимость условий T5 |
| `*.themes` | Количества по подтверждённым темам |
| `previous_source_levels` | Индексы ранее использовавших исходник уровней, включая ё/е |
| `source_eligible`, `source_assessment`, `bypass` | Предварительный допуск, оценка и применённое исключение |

Для T1 берётся **только** `recognizable.count_4plus`, для T2 —
**только** `recognizable.initial_4plus`. Ключи длин в JSON — строки.
Профили измеряют также исключённых/неуверенных кандидатов, чтобы сохранять
объяснимость отсева. Предварительный допуск исходника не является выбранным
уровнем. Общая уникальность T3/T4, окончаний T5 и тем T6 относится к следующему
генератору, не к этому кэшу.

Ключ охватывает содержимое словаря, манифеста, частотного списка и универсума,
дампа, БД, обработанных подсказок, категорий/семантического снимка при наличии,
исторических уровней, конфигов, списка исключений определений, таксономии,
общих hint-векторов и влияющего кода Python/JVM. Пути и mtime ключ не меняют.
Промежуточные признаки имеют отдельный кэш; смена оценок/истории не требует
повторного разбора дампа. Gzip детерминирован (mtime=0), содержимое защищено
хэшем; повреждение или несовместимость дают ошибку.

`build/reports/level_profiles/summary.json` фиксирует время всего вызова,
размер кэша, попадание, количества и все входные хэши.
`LEVEL_PROFILES.md` в той же папке сохраняет построчный отчёт без определений:
частоту и статус корпуса отдельно от источника и результата оценки.

## Проверки

`python3 -m unittest discover -s tools/tests -p test_level_profiles.py`:
ручной подсчёт на маленьком словаре, ё/е, анаграммы, повторные буквы, 3/4+,
окончания с длиной, темы, история исходников, корпусный ноль, порог частоты,
пометы, исключения владельца, проверка снимков, JVM-происхождения, экспорт БД
с guessable=0, сохранение религиозных/исторических структурированных тегов,
инвалидация каждого входа, детерминизм, повреждение кэша,
длины 10+ при JSON roundtrip и полный синтетический конвейер с повторным чтением.
