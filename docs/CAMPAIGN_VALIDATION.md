# Независимая проверка кампании — GEN-04

`tools/validate_campaign.py` проверяет кандидат GEN-03 без импорта генератора,
его индекса, расписания или предикатов. Поля `installable`, `status`, отчёт
GEN-03, готовые множества, числа и флаги из `payload.profiles` не используются
как доказательства. Снимок GEN-01 нужен только для наблюдаемых частот,
лексических признаков, оценок пригодности LEX-04 и категорий LEX-03.
Составимость и все множества ответов пересчитываются заново через `Counter`
на текущем `words.txt`; исходник исключается до проверки заданий.

```sh
python3 tools/validate_campaign.py
python3 -m unittest discover -s tools/tests -p test_campaign_validation.py
bash ./gradlew :core:test --tests 'com.example.sostavslova.core.CampaignDatasetAuditTest' --console=plain
```

По умолчанию кандидат — `build/reports/campaign/campaign.json`, снимок берётся
из summary GEN-01. Можно передать `--campaign`, `--profiles`, `--words`,
`--previous-levels`, `--database`, `--manifest`, `--output`.
Проверяются SHA-256 содержимого снимка и его привязка к текущим словарю,
старым уровням, БД и манифесту. В отчёт записываются хэши входов и обработчиков.
Дамп не регенерируется, сеть не используется, приложение и `data/` не меняются.

## Что проверяется

- 30 разных исходников, 6 этапов, 100 заданий/звёзд, расписание M/R,
  разные типы внутри уровня, ротация Мастера с T6/T7.
- 8–15 старых исходников и диапазоны узнаваемых ответов
  40–300 / 70–380 / 100–460 / 130–540 / 160–620 / 250–700.
  Это решения владельца из `CAMPAIGN.md`, заменившие прежний минимум 10
  старых слов и прежние нижние границы.
- Все 32 буквы; запреты на роли исходника и назначенных целей; длины,
  пригодность, частота, жёсткие лексические исключения. Предпочтение трём
  исходникам владельца отражается в отчёте, но не становится новым запретом
  остальных исходников.
- Все 435 Jaccard по **заново посчитанным узнаваемым** ответам: среднее ≤3%,
  максимум ≤15%. Для каждой пары сохраняются пересечение и объединение.
- Кривые параметров по появлениям типа, границы параметров, 4+ только для
  T1/T2, совместное условие окончания и длины T5, вхождение буквы в T7
  как число слов, а не число повторений буквы.
- Резервы `ceil(k*N)`: k=3 / 2,5 / 2 для десяток уровней; N=1 для T3/T5,
  число загадок для T4, n для счётчиков. Резерв T4 измеряется до назначения
  и включает только узнаваемые слова с реально пригодной подсказкой.
- Общая нормализованная уникальность целей T3/T4, окончаний T5 и категорий
  T6; отсутствие соседнего повтора T2; редчайшая выполнимая буква T7.
- T6: известная категория из таксономии, минимум 40 узнаваемых слов глобально,
  полный локальный набор по словарю, включая неузнаваемые допустимые ответы.
- Каждая назначенная T4-цель проверяется по реальным определениям, формам и
  родству из БД. Готовое `useful` из профиля не читается.

Оценки узнаваемости и семантические категории остаются входом LEX-03/LEX-04,
а не результатом независимой экспертной семантической оценки GEN-04.
Категории могут быть частичными; неизвестные темы не создают резервы.

## JVM и Python

`core:auditCampaign` принимает два пути: входной JSON-пакет и выходной JSON.
Пакет содержит `campaign`, `dictionary`, `hintInputs` и `production`.
В штатном запуске валидатор сам создаёт временный пакет и запускает Gradle.
Полные тексты определений и подготовленные подсказки не попадают в отчёты
и репозиторий; временный пакет удаляется после проверки.

JVM декодирует кампанию в модели `core`, вызывает структурный/производственный
валидаторы, строит ответы через `WordIndex`/`GameState`, проверяет каждое
задание отдельно через `TaskRules.submit`. Ввод **всех** ответов должен дать
M; повторные буквы проверяются реальным индексом. Python сравнивает полные
принимаемые наборы, требуемое число ответов и прогресс от каждого одиночного
слова. Это ловит, например, ошибочный зачёт повторений буквы как нескольких
слов в T7.

Для каждого сочетания из R заданий вводится объединение индивидуальных
свидетелей, затем проверяется реальный переход `CampaignRules.recordLevel`.
Одновременное выполнение других заданий допустимо. Все ветки проверяются
на достижимой границе; они композиционны, поскольку ответы и задания
локальны уровню, а доступ необратим. Отдельно исполняется вся цепочка до
финала и цепочка полного добора до 100 звёзд. Для штатного расписания это
155 сочетаний, включая все пять сочетаний 4 из 5 на последнем уровне.

Для T4 сравниваются результаты `DefinitionHint.prepare` и Python `prepare`
для всех легальных ответов уровней с загадками, включая слова вне резерва.
Дополнительно JVM проверяет лестницу назначенных загадок и бесплатные шаги.
Синтетические общие входы — `tools/campaign_validation_vectors.json`;
тесты включают повторные буквы, ё→е, 3 против 4+, T3, T5/T6/T7,
маскирование форм/родства и невозможные задания. Отдельная синтетическая
30-уровневая JVM-кампания проверяет M/R, 100 звёзд и все 155 веток.

Если Gradle недоступен, есть `--jvm-classpath` и `--java`: ими можно запустить
**свежескомпилированные** `core` и `CampaignDatasetAudit` напрямую. Это
альтернативный способ исполнения той же JVM-проверки, без пропуска правил.
Свежесть внешнего classpath обеспечивает вызывающий. Отсутствие JVM или
ошибка запуска всегда запрещает выдачу проверенной копии.

## Отказ и результаты

В `build/reports/campaign_validation/` сохраняются:

- `validation_report.json`: полный независимый пересчёт и JVM-итог;
- `unreachable.json`: недостижимые задания и ветки;
- `balance_deviations.json`: нарушения структуры, назначений и балансировки;
- `parity_deviations.json`: расхождения Python/JVM и ошибки исполнения JVM;
- `validated_campaign.json`: проверенная копия, **только** при полном успехе.

Любое нарушение даёт код 2. Старая проверенная копия удаляется **до** чтения
входов, включая случай испорченного JSON. Одна только успешная Python-проверка
не выдаёт копию. Диагностика задания содержит `level`, `task`, `code`, `reason`;
ошибки всего пакета имеют пустые адреса. Установщика в GEN-04 нет; следующая
задача не должна обходить этот отказ или устанавливать исходный кандидат по
старому флагу GEN-03. Проверка не разрешает публичный релиз и не заменяет аудит
прав на определения.

## Проверенный снимок 2026-11-11

Кандидат SHA-256:
`bd3ed4ac72c1121baabfbff5855c5fec901cca31887948938fc419dcc9638a50`.
Входы словаря, БД и снимка LEX привязаны хэшами в локальном отчёте.

Пересчёт подтвердил все 100 заданий, 155 веток R и финал; 8 старых исходников,
все 32 буквы, три предпочтительных исходника. Средний Jaccard —
**2,9971776516%**, максимальный — **14,5985401460%**.
Недостижимых заданий и нарушений балансировки не обнаружено.

Кандидат получил **код 2**, `installable=false`: найдено 29 адресованных
расхождений T4 в 15 разных словах: баки, батек, злыдня, кека, лета, полом,
прог, птах, раба, сверка, сир, сонь, тин, тора, хав. Среди них «раба» входит
в узнаваемый пул. JVM выбирает определение, начинающееся с «форма», Python
отклоняет его как ссылочное; у «сир» Python выбирает другое определение.
Это связано с разным поведением `\b` после кириллицы в регулярном выражении
отказа от ссылочных определений. Все назначенные T4-цели и их лестницы JVM
прошли; расхождение обнаружено при более полной проверке местных пулов.
Проверенная копия не создана, кандидат в приложение не установлен.
Исправление обработчиков подсказок остаётся отдельной задачей; критерий
равенства ради успешного результата не ослаблен.

Проверки: 231 тест tools и 118 тестов JVM core прошли. JVM-исходники собраны
локальным Kotlin 2.2.10 с target 21; тесты исполнены JUnit Platform на JDK 21.
Штатные Gradle-команды не исполнились из-за запрета записи глобального кэша
Gradle в текущем окружении. Полный gate оставлен внешнему оркестратору.
На испорченном кандидате T2 уровня 6 с буквой «я» подтверждены код 2,
адрес `level=6 task=l06-t2`, причины недостижимости и отсутствие старой
проверенной копии. Android/устройство и release в GEN-04 не проверялись.
